# 14 面试讲解指南

## 1 分钟项目介绍

这是一个基于 Spring Boot 3 的校园二手交易平台，面向校内学生闲置物品交易。项目覆盖注册登录、商品发布、图片上传、商品审核、商品浏览、下单、模拟支付、订单取消、确认完成、评价、举报处理和后台运营管理。后端使用 Spring Security 6 + JWT 做认证授权，MyBatis-Plus 操作 MySQL，Redis 缓存分类和热门商品。核心亮点是通过商品状态机、订单状态机和事务控制，完成从商品发布到交易完成的业务闭环。

## 3 分钟项目介绍

项目最初是一个校园二手交易后台管理系统，我把它升级设计为 `campus-market-platform`，定位是校园二手商品交易与运营管理平台。

用户侧主要有三条流程：

1. 卖家发布商品，上传图片，商品进入待审核状态。
2. 管理员审核通过后，商品进入在售状态。
3. 买家浏览商品、下单、模拟支付、线下交付后确认完成并评价。

后台侧有两个运营闭环：

1. 商品审核闭环：待审核、审核通过、审核驳回、审核日志。
2. 举报处理闭环：用户举报、管理员处理、下架商品或驳回举报、操作日志留痕。

技术上采用单体模块化架构，没有做微服务。交易相关操作使用事务保证一致性，例如创建订单时通过条件更新把商品从 `ON_SALE` 改为 `LOCKED`，然后创建订单；如果条件更新影响行数为 0，说明商品已被锁定或售出，订单创建失败。

## 5 分钟项目介绍

这个项目解决的是校园内二手商品交易信息分散、交易流程缺少管理、违规商品难以处理的问题。我把系统设计成两个核心闭环：交易闭环和后台运营闭环。

交易闭环从卖家发布开始。卖家填写分类、标题、描述、价格、成色、交易地点和图片，提交后商品进入 `PENDING_AUDIT`。管理员审核通过后，商品变为 `ON_SALE`，游客可以浏览，登录用户可以下单。买家创建订单时，系统会校验商品必须在售、买家不能购买自己的商品，并使用带状态条件的更新语句锁定商品，防止多个买家重复购买。创建订单成功后订单为 `CREATED`，商品为 `LOCKED`。买家模拟支付后，系统写入 `payment_record`，订单变为 `PAID`，商品变为 `SOLD`。线下交付完成后，订单变为 `FINISHED`，买家可以评价。

后台运营闭环包括商品审核和举报处理。商品审核会写 `goods_audit_log`，管理员下架商品、处理举报、禁用用户会写 `admin_operation_log`，保证关键操作可追溯。

技术实现上，我选择 Spring Boot 单体模块化，适合本科实习项目。认证使用 Spring Security 6、JWT 和 BCrypt；数据库使用 MySQL；缓存使用 Redis 缓存分类列表、热门商品、浏览量和未读消息数；前端第一版使用原生 HTML 页面演示，后续可升级 Vue 3。项目没有做真实支付、微服务、复杂 RBAC、WebSocket 和消息队列，因为这些会扩大项目边界，不利于稳定演示。

## 核心技术问题

### 1. 为什么创建订单要锁定商品？

校园二手商品通常是一物一件。如果两个买家同时下单同一商品，会造成重复交易。创建订单时把商品从 `ON_SALE` 改为 `LOCKED`，可以阻止第二个买家继续下单。未支付订单取消时，再恢复为 `ON_SALE`。

### 2. 创建订单如何避免并发重复购买？

不是简单先查再改，而是使用带状态条件的更新：

```sql
UPDATE market_goods SET status = 'LOCKED' WHERE id = ? AND status = 'ON_SALE';
```

如果影响行数为 1，说明锁定成功；如果为 0，说明商品已经不在售，订单创建失败。该更新和订单创建放在同一个事务中。

### 3. 为什么不接真实支付？

真实支付需要商户资质、支付回调、验签、退款、对账等复杂流程，会扩大项目边界。这个项目重点是业务闭环和状态流转，所以用模拟支付生成支付记录并推动订单状态变化。

### 4. JWT 和 BCrypt 分别解决什么问题？

JWT 用来解决登录后的身份识别，前端每次请求携带 Token，后端解析出用户 ID 和角色。BCrypt 用来保护密码，数据库只保存密码摘要，不保存明文密码。

### 5. 如何防止用户越权？

接口层判断是否登录和角色，Service 层做资源归属校验。例如修改商品校验当前用户是否为卖家，取消订单校验当前用户是否为买家，查看订单校验当前用户是否为买家、卖家或管理员。

### 6. Redis 缓存了哪些内容？

缓存分类列表、热门商品、浏览量增量和未读消息数。这些数据读多写少，或者允许短时间不完全一致。订单状态、支付状态和商品锁定状态不缓存，避免影响交易一致性。

### 7. 商品审核为什么不单独设计 audit_status？

为了避免状态重复和矛盾，商品审核阶段直接体现在 `goods.status` 中，例如 `PENDING_AUDIT`、`REJECTED`、`ON_SALE`。审核过程和原因通过 `goods_audit_log` 保存。

### 8. 后台操作日志有什么价值？

用于追踪管理员关键操作，例如审核商品、下架商品、处理举报、禁用用户。这样出现争议时可以追溯是谁在什么时间做了什么操作。

## 业务难点

| 难点 | 解决方案 |
| --- | --- |
| 商品和订单状态一致 | 用事务封装创建订单、取消订单、模拟支付 |
| 防止重复购买 | 下单时条件更新商品 `ON_SALE -> LOCKED` |
| 审核前不能购买 | 商品发布后进入 `PENDING_AUDIT`，通过后才 `ON_SALE` |
| 用户越权 | Service 层做买家、卖家、管理员身份校验 |
| 举报处理可追溯 | 保存举报处理结果和管理员操作日志 |
| 缓存一致性 | 核心交易不依赖缓存，缓存失败降级 MySQL |

## 项目不足

1. 支付是模拟支付，没有真实第三方支付回调和对账。
2. 消息是站内消息，没有 WebSocket 实时聊天。
3. 权限只有 `USER` 和 `ADMIN`，没有复杂菜单权限。
4. 商品推荐是简单热门排序，没有个性化推荐算法。
5. 第一版文件上传使用本地目录，后续可以替换为 MinIO。
